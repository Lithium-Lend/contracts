# Testnet monitoring and response

The current LiteForge deployment remains a valueless test environment. The maintainer has deferred multisig, delayed governance, and a separate emergency guardian to mainnet. Independent-review enforcement is deferred while there is only one collaborator. Stranded-donation recovery is deliberately out of scope.

`comet/config/liteforge-attestation.json` records the reviewed deployment baseline. It pins all current market components, proxy implementation/admin slots, governors, guardians, token owners, adapter configuration, and DIA wrapper owners, pairs, backing addresses, decimals, and runtime hashes. A configuration match is not proof that an oracle price is economically correct.

Run `node script/attest-liteforge.mjs --output attestation/latest.json` from the repository root. It only uses read-only RPC methods, captures one block, and fails if a configured component, role, feed, or code hash changes. RPC failure and stale/invalid oracle rounds fail rather than skip. `--block 65692029` reproduces the reviewed reference block; a historical check does not replace latest-state monitoring.

Health alerts are separate from integrity failures. Default thresholds are 70% collateral-cap warning, 90% critical, 100% full, and less than 1% available base cash relative to supplied base claims. Negative reserves are critical. Native cash uses `accountedNative`, so forced donations cannot conceal a liquidity shortage. These are testnet operational thresholds, not approved mainnet risk parameters. Use `--fail-on-health` in the scheduled monitor to surface critical alerts as a failed job.

On an unexpected implementation, role, source configuration, or runtime change, preserve the failed artifact and compare the transaction history with the approved change. Do not automatically replace the baseline with the observed value. Investigate oracle redirection or invalid rounds before restoring risk-taking operations. Monitoring has no signing key and cannot pause or upgrade anything itself.

For capacity alerts, distinguish collateral admission from available base liquidity. A full collateral cap does not itself block repayments. Do not confiscate healthy positions, remove risk limits, or silently migrate addresses. Use withdrawals from controlled test fixtures only where appropriate, or review a cap change/new test market with explicit user communication. Any new real-value cap requires liquidation-depth, oracle, reserve, and loss-budget analysis.

For low base cash, repayments or voluntary supplier liquidity can restore cash. Do not promise immediate full withdrawals from a highly utilized pool. A low cash alert alone is not a proof of insolvency. There is no automatic faucet claim, mint, deposit, administrative transaction, or external message in the monitor.

Before mainnet, replace the accepted testnet authority assumptions, confirm genuinely independent price validation or a reviewed source-governance arrangement, appoint independent reviewers, and have the final deployed source/bytecode reviewed. Existing checks must stay enabled throughout this transition.

The required `validate` check includes all three pinned fork suites and independent static analysis. Fork JSON is checked for missing or skipped suites. The deployment workflow also runs every six hours and can be dispatched manually. Scheduled integrity, critical liquidity, and incomplete explorer assurance checks fail visibly and retain their JSON artifacts for 30 days. GitHub Actions notifications must be enabled for the maintainer; no external notification recipient is configured.

`node script/check-explorer.mjs` inventories all 26 active protocol components and external wrappers. Full verification requires published source and explicit, consistent full-verification flags. Partial, published-unclassified, unverified, and unknown are separate states. HTTP failures never become verification success. Historical deployment manifests are retained as historical evidence; use the attestation baseline and collateral-cap upgrade record for current implementations and asset lists.

From `comet`, `node script/verify-current.mjs --check` checks compiler input and constructor arguments for the six current cap-upgrade components plus ten retained additional-market components. Each submission contains only the target's required source units, keeping every source byte and compiler setting unchanged except output selection. `current-verification-inputs.json` pins the nine derived inputs. CI recompiles them with Solidity 0.8.15 and requires identical creation bytecode, runtime, and metadata against the reproduced complete deployment build. This avoids sending unrelated compilation targets to the explorer. Historical complete deployment inputs remain authoritative and unchanged.

`--submit <address>` publishes a multipart source request to the explorer for one explicit address and saves a separate observation under `attestation/`, including both deployment and submitted input hashes. It never modifies historical manifests or sends a chain transaction. Submission or an 'already verified' message alone is not full verification. Explorer indexing and verifier availability can still prevent confirmation. The original USDC deployment and token verification tooling remains separate because its exact compilation context differs.

Oracle preparation for mainnet: select an independently administered reference for each pair, document freshness and decimal assumptions, and calibrate a deviation bound using observed data and liquidation needs. Any replacement adapter should pin the intended wrapper/backend/pair and normalize both sources before comparison, reject invalid rounds, and have an explicit recovery policy after source rotation or disagreement. Configuration pinning alone cannot establish economic price correctness because an unchanged backend can still publish an incorrect fresh value. No speculative adapter or feed migration is deployed by this change.
